# 마이그레이션 — 스키마가 바뀔 때 쓰는 방식

## 어디에 두나

`db/migrations/` 안에 `.sql` 파일 하나. 이름은 **네 자리 번호 + 하는 일**로 짓는다.

```
db/migrations/0001_push_subscriptions.sql
db/migrations/0002_무엇을_한다.sql
```

번호 순서대로 적용되므로 다음 번호를 이어서 붙인다.

## 어떻게 적용하나

```
npm run db:migrate     # 아직 적용하지 않은 것만 순서대로 적용
npm run db:check       # 표와 칸이 06-data.md 와 맞는지 확인
```

적용 이력은 `schema_migrations` 표에 파일 이름으로 남는다. 그래서 몇 번을 돌려도
이미 적용한 파일은 다시 돌지 않는다. `schema_migrations` 는 06 의 저장 항목이 아니라
이 도구가 쓰는 장부다.

`npm run db:push` 는 `db/schema.sql` 전체를 적용한다 — **아무것도 없는 새 DB** 를
한 번에 세울 때만 쓰고, 이미 쓰고 있는 DB 를 바꿀 때는 쓰지 않는다.
(새 DB 를 세운 뒤에는 `npm run db:migrate` 를 한 번 돌려 이력을 맞춘다.)

## 파일을 쓸 때 지킬 것

- **파일 안에 `BEGIN` · `COMMIT` 을 적지 않는다.** 한 파일이 곧 한 트랜잭션이다 —
  실패하면 그 파일의 변경이 전부 되돌아간다. 적혀 있으면 실행이 거부된다.
- **이미 적용한 파일은 고치지 않는다.** 고쳐도 다시 돌지 않는다. 새 번호로 하나 더 만든다.
- `CREATE TABLE IF NOT EXISTS` · `ADD COLUMN IF NOT EXISTS` 처럼 **다시 돌려도 탈이 없게** 쓴다.
- 표 · 칸은 `docs/06-data.md` 에 있는 것만 만든다. 한도 · 상태값은 `docs/05-policy.md` 의
  P 번호를 주석으로 함께 적는다. 06 에 없는 것이 필요하면 **먼저 팀에 묻는다.**
- 같은 변경을 `db/schema.sql` 에도 반영한다 — 그 파일은 **지금 스키마의 전체 모습**이고
  새 DB 는 거기서 만들어진다. 두 곳이 어긋나면 새로 세운 DB 만 다른 모양이 된다.

## 데이터를 지우거나 칸을 없애는 변경

`DROP` · `ALTER ... TYPE` 처럼 되돌릴 수 없는 것은 **팀에 먼저 확인**하고, 무엇이
사라지는지 파일 맨 위 주석에 적는다.
